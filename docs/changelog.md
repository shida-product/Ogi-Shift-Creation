## 2026-08-22: 希望休・シフト生成の月開放ルール更新（各月16日以降は約半年先まで開放）

- **開放上限の変更**（`js/month-window.js`）:
  - 1〜15日: 今日の年月 + 4ヶ月（例: 8/1〜8/15 → 12月まで、9/1〜9/15 → 翌1月まで）
  - 16日以降: 今日の年月 + 5ヶ月（例: 8/16〜8/31 → 翌1月まで、9/16〜9/30 → 翌2月まで）
  - これにより、毎月16日を迎えると約半年先（5ヶ月先）まで月が開放され、希望休の入力・シフト生成が可能になります。

## 2026-08-04: 勤務確定日（work_ebisu / work_shibuya）の追加

### 追記: モバイルカレンダーのレイアウト崩れ修正
- 月グリッドのラベル「〇〇 勤務（恵比寿／渋谷）」が長く、列幅が押し広げられて金・土曜が画面外にはみ出していた
- 月グリッドの表記を「〇〇 勤務」に短縮（店舗名は日付タップの詳細シートで確認できる）
- `.calendar-grid` の列を `repeat(7, minmax(0, 1fr))` に変更し、今後長いラベルが入っても等幅を維持（あふれた分は省略記号で切り詰め）
- 勤務確定バーは中抜き表示に変更：白背景＋スタッフ色の枠線・文字。
  塗りつぶし（希望休）と中抜き（勤務確定）で一目で区別できる。
  店舗カラー下線方式は色がゴチャつくため廃止。店舗は日付タップの詳細シートで確認する。
  連日登録の場合は繋ぎ目に縦線が出ないよう辺ごとに枠線を描画

### 1. 希望休の種別に「勤務（恵比寿）」「勤務（渋谷）」を追加
- 全スタッフ共通。勤務が確定している日を店舗指定で登録する
- DB: `shift_requests.request_type` の CHECK 制約に `work_ebisu` / `work_shibuya` を追加（`sql/add_work_request_types.sql`）
- トンマナは生成画面の店舗カラーに統一（恵比寿 `#2D4FBF` / 渋谷 `#E879A8`）。
  希望休ページ：休み希望系＝淡背景、勤務確定＝塗りつぶしで区分を視覚的に分離
- 生成画面：希望休は網掛け（斜線）のまま、勤務確定は網掛けを使わず**セル下端に店舗カラーの実線3px**。
  網掛けの色違いだと32pxの勤務マーカーと同系色で溶けるため、質の違う表現に分けた。
  `is-warning`（inset box-shadow）・`is-manual`（`::after`）と衝突しないよう `::before` で描画

### 2. 生成ロジックはハード制約として最優先で反映
- 日付ループの先頭で事前配置し、以降のロジックは上書きしない（上書きできるのは手動調整のみ）
- 勤務パターンは区分から自動決定（社員・特別枠 → `○店舗` / パート → `☆店舗`）
- `addAssignment()` 経由のため、勤務日数・連勤カウント・店舗充足カウントにそのまま算入される
- `computeRestDays()`：勤務確定日は公休候補から除外（小野の日曜自動公休・6連勤潰しの補正も対象外）
- `canWork()` / `canWorkHalfDay()` / 事務配置ループ：`isLocked()`（手動調整 or 勤務確定）で二重配置を防止
- 事務が確定で埋めた店舗はその日の自動配置をスキップ（3人目を入れない）

### 3. 条件チェックパネルに G3「勤務確定が全て反映されている」を追加
- 店舗まで一致しているかを判定。確定登録がある月のみ表示
- 確定を優先した結果として連勤上限・公休数を超えた場合は、生成を止めず既存の各チェック項目が警告を出す

## 2026-03-25: 配置均等化・Undo/Redo・集計列

### 1. 事務パートの配置均等化（debtベース）
- **旧**: 累積ペース + 優先度ベース → メインスタッフ（木庭・諫早）が前半に集中
- **新**: 負債（debt）ベースのスコアリングに変更
  - `debt = (target × progress) - actual` で「今この時点で何日遅れているか」を算出
  - debtが大きいスタッフが優先的に出勤 → 月全体で自然にインターリーブ
  - priorityは同debtスタッフ間のタイブレーカーに格下げ

### 2. 徳永のペース配分閾値
- `ahead > 0.15` → `ahead > 0.08` に変更（前半固め打ち防止を強化）

### 3. 木庭の連勤上限
- `max_consecutive_days: 4` をDB（work_conditions）に追加
- 諫早と同じ4連勤上限に統一

### 4. Undo/Redo/Reset機能
- 手動セル変更の履歴管理（最大50件）
- Reset: シフト生成直後の状態に戻す
- `generate.html` にボタン追加済み

### 5. ガントチャート集計列
- スタッフ名の右横に出勤数/公休数を表示
- スタッフ別の閾値で色分け（白/黄/赤）

### 6. 条件チェック文言の簡潔化
- 各チェック項目の`text`を短く読みやすく修正

### 7. 生成パラメータ改善
- 試行回数: 8 → 30

### 8. シフト再生成・リセット時の手動変更フラグ（赤バッジ）クリア修正
- **課題**: シフト再生成やリセット後も、手動変更を示す赤バッジが残り続けるバグが存在した。
- **原因**: 以前の「悪化防止ロジック」（再生成結果のスコアが既存より低い場合に既存状態を維持する）によって、以前の手動変更データが維持されていたため。
- **対応**: Undo/Reset機能があることを前提とし、悪化防止（既存維持）ロジックを撤去。シフト再生成時は常に新規の生成結果を採用し、手動変更フラグが確実にクリアされるよう修正。またリセットボタン押下時にも明示的にフラグをクリアするよう安全策を追加。

## 2026-03-25: 条件チェックロジックのリファクタリング

### 背景
`scoreShifts()`（スコアリング）と`renderConditionsCheck()`（UIパネル表示）で
同一のチェックロジックが約400行にわたり二重実装されていた。
片方を修正してもう片方を忘れるとバグが発生する温床になっていた。

### 変更内容

#### 1. `runAllChecks()` 共通関数の導入
- 全チェック項目を実行し、構造化データ（`globalItems`, `staffChecks`, `bonusItems`）を返す
- `scoreShifts()` と `renderConditionsCheck()` の両方がこの結果を利用

#### 2. ヘルパー関数のモジュールレベル昇格
以下の関数を `renderConditionsCheck` 内部のクロージャからモジュールレベルに移動：
- `_staffAssignments`, `_workDays`, `_restDays`, `_countPattern`
- `_maxConsecutiveWork`, `_maxConsecutiveWorkIncludingDispense`
- `_countSundays`, `_checkConsecutiveRestPairs`
- `_restOverlap`, `_countCrossStore`, `_getWeeklyBreakdown`, `_dispenseCount`

#### 3. `scoreShifts()` の簡素化
- 旧: 独自にチェックを実行（〜160行）
- 新: `runAllChecks()`の結果から`scoreDelta`を合算するだけ（〜30行）

#### 4. `renderConditionsCheck()` の描画専用化
- 旧: 独自にチェックを実行（〜390行）
- 新: `runAllChecks()`の結果をUIに描画するだけ（〜105行）

### コード量の変化
- **Before**: 2320行
- **After**: 1993行（**-327行**）
